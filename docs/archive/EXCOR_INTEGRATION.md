# Archived eXcor integration record

**Superseded on 2026-10-29 at the user's request.** This file preserves implementation/test history only. eXcor is not part of the active Rynx build; the upstream repository was not changed. The current Android providers are InnerTubeX → NewPipeExtractor. See [`EXCOR.md`](EXCOR.md).

Pinned commit: deb51bafc219645133f3f9145a68719cade7165e. Excor is the primary YouTube engine. The Android stream resolution order is Excor → InnerTubeX → NewPipeExtractor. InnerTubeX v0.11.2 is used through its published KMP API; NewPipeExtractor remains Android-only. Rynx writes adapters and provider orchestration only, not extractor internals.
Integration: `dependencies/eXcor` is included as a Gradle composite build and `com.bxane.excor:excor:1.0.0` is substituted with the pinned checkout. `providers:excor` shares its public-API adapter between JVM and Android; the host uses OkHttp, a logged-out session, and a disabled/no-op Excor config store. Android search calls Excor Music search and continuation paging. Android stream resolution asks Excor first, then InnerTubeX for ordinary direct HTTPS audio, then NewPipe; cancellation and explicit provider refusals propagate immediately, so the chain does not bypass age, sign-in, region or availability restrictions.

Implemented adapter surface: search result and playlist item mapping, largest valid thumbnail selection, nullable/negative duration handling, search and playlist continuation mapping, audio stream resolution, refusal forwarding, session-change forwarding, and stable failure classification. Resolved URLs and headers are short-lived; their `toString` omits sensitive values, the Android header registry is bounded and in-memory, and Media3 attaches provider headers at request time. Cancellation is rethrown and user-facing provider errors omit transport details. Android catalog track rows now start Media3 playback; the fallback uses NewPipe only when Excor cannot resolve the selected stream. Playlist detail browsing, downloads, and durable offline behavior remain incomplete.

Tests: JVM mapper/redaction tests and fallback-order tests pass. The shared `AudioStreamResolver`, short-lived `ResolvedAudioStream`, Excor-first `AudioResolutionChain`, and discovery preparation now live in `shared/playback/commonMain`; both Excor and the Android NewPipe fallback adapt to those contracts. Android URL-header routing and Media3 session instrumentation compile, but were not executed on a device. The final local deterministic gate passed provider/shared tests and built both Android APK variants.

2026-10-28 continuation: the opt-in live YouTube smoke test was attempted and failed before a provider response with `java.io.IOException` in the network connection path (`ConnectPlan.kt:472`, connection refused). It emitted no media URL or header. Live search/extraction and audible streaming therefore remain unverified; see `docs/parity/BLOCKERS.md`.

InnerTubeX is initialized with the host-owned Ktor `HttpClient`; its own documented extractor and cipher/config APIs are used. Requests disable HLS, SABR and bounded-range output because the current Rynx playback contract and Media3 source path cannot consume those transports. Returned streams must have matching video IDs, HTTPS URLs, audio MIME types and no segmented-range requirement. Explicit access refusals never continue down the provider chain; network errors and unsupported transport results may. Tests cover provider order, cancellation, explicit refusals, direct stream mapping, transport capability constraints and invalid IDs.

The signatures above were checked against the approved libraries' public API declarations and documentation only. No sample application queue/controller was reused and no extraction algorithm was reimplemented. JitPack resolution, current network extraction and audible device playback remain runtime-unverified until the Gradle build and live checks pass.
